Making two sales systems agree

Problem

The sales reporting portal and the company's compensation system showed different numbers for the same measures, such as activations and gross profit. Without a clear rule for each gap, it was hard to tell which figure was right.

What I tested

I compared the two systems down to individual devices for a sample market and wrote down every rule behind the differences: which month an activation counts in, how chargebacks and early returns are excluded, what counts as paid, and which stores are in scope. I also checked payroll records from a time-tracking tool against sales data, matching employee IDs and role groups, and worked with the data team on report mismatches.

What I built

A monthly retention report that follows the compensation system's rules, with a paid-device funnel that matches its definitions, plus safeguards on the related retention APIs.

Result

A written rule set that explains each difference between the systems, and a report built to match it.

QA

Fixing "view as employee" for admins

Problem

Administrators can switch into an employee's view of the HR portal. In that mode, opening the employee home page broke other pages, including Policies and My Tickets.

What I found

The home page was clearing the session cookie that the employee view depends on. I specified the fix along with its tests and documentation, and coordinated the service restart and server permission changes with the system admins.

I then checked the rest of the employee view and found two more issues: the schedule page didn't show the banner that marks the view, and the help center showed the admin layout. I wrote fix specifications for both.

Result

One defect traced to its root cause with a specified fix, and two related defects documented with fixes specified.

Attendance corrections backed by device data

Problem

Employees couldn't submit attendance corrections, and HR couldn't see them in its review queue. The fix also needed to show HR the attendance device records for each request.

What I built

I restored employee submission and the HR review queue. I connected read-only clock-in records from the attendance devices through limited database access and an employee-code mapping, then added an API for time adjustments and a "Device punches" column for HR.

Design decision

The feature keeps a record of each correction and does not write anything back to payroll.

Result

Corrections reach HR with the device records alongside them.

How I work

The same loop on every defect or feature, whether I end up writing the fix or handing over a spec.

  1. Reproduce

    Confirm the issue on the development environment with real steps.

  2. Find the cause

    Read the code and query the database until the reason is clear.

  3. Write the spec

    Describe the fix, the tests and the edge cases before any code changes.

  4. Build

    Implement in React, Python or Go, depending on the system.

  5. Test both ways

    Positive and negative cases, backed by pytest or Go tests.

  6. Verify on dev

    Check the change on the live development site before handing it over.
